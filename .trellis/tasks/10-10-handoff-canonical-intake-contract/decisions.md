# 交接修复决策记录

## 已定范围与授权

- 用户明确要求正式创建修复任务，持续决策最佳实践；方案形成后停下来获取批准，实施阶段按计划完成修复、提交推送、必要发布、重装、落点更新和任务收敛。
- 用户随后明确批准已封口的完整修订包进入实施，并授权推进修复、提交推送、必要发布、重装、落点更新与任务收敛；批准发生在两份 revision 1 方案 seal 之后。
- 实际产品修改目标为本 `pennix-skills` 仓库的 `skills/pennix-session-handoff/`；根侧任务只协调固定、部署证据和组合验收。
- 已确认缺口：消费字段漏校验、两处完整投影冗余、无界历史与全文必读之间的操作合同缺口。当前原包未损坏，不能将首次截断推断为所有读取方法不可行。
- 不改变任务/归属权威、不写安装副本、不改历史交接、不纳入其他设备和无关漂移；主会话 inline 交付，不默认派发独立审查节点。

## D1：接纳阅读合同

- 影响：决定必读内容、阅读完成声明、大包验收和后序格式设计，是当前最高优先级就绪选择。
- 依据：现有包 42.78 MiB、2,071 条正文和数万来源记录；全部正文可无损分段；当前合同要求全文读取，实际阅读声明是协调代理自报。
- 选项 A（推荐）：必读交接核心、当前任务与重要决定/风险，完整历史保真保留并按需查阅；程序全量验证格式和来源，接纳如实声明实际阅读范围。
- 选项 B：继续要求所有候选正文与来源记录全文阅读，提供无损分批和明确完成规则；阅读成本随历史增长。
- 推荐理由：保留可追溯历史与当前事实核验，同时使接管成本围绕当前任务；避免把机器解析误称为全文语义阅读。
- 实际答复：用户通过原生 `request_user_input` 选择“核心必读、历史按需（推荐）”。
- 已定合同：必读当前任务、重要决定和风险；完整历史保真保留并按需读取；程序全量校验，代理如实声明阅读范围。此答复是设计选择，不是实施批准。
- 后序依赖：接下来核验单文件规范投影与 core/历史分离的消费、绑定和归档影响，再提出格式边界选择；旧 schema 兼容和读取完成声明留到格式明确后。
- 返回动作：继续必要的本地接口核验，形成下一轮依赖已满足的重要选择。

## D2：规范内容的文件边界

- 依赖：D1 已选“核心必读、历史按需”；两种表示均保留完整历史并由程序全量校验。
- 接口事实：`handoff.py:_archive_snapshot/_archive_copy/lifecycle_retention` 目前只接受并处理 JSON/prompt 配对；归属封口将 JSON 文件摘要传给原生 Trellis。完整历史若拆出，需增加引用绑定并同步生成、归档、恢复和清理，防止核心仍在而历史缺失。
- 选项 A（推荐）：保留一个 JSON，历史仅存于一个规范位置；原生只读入口输出必读核心视图，历史按需定位。原例去掉重复投影后约 20.71 MiB，程序仍全量校验；视图不是全文阅读声明，也不另建持久消费台账。
- 选项 B：小 core JSON 与完整历史附件分离，prompt 随 core 配对；core 绑定附件，所有文件整体复制、验证、归档和恢复。人工阅读边界直观，但新增第三个必需文件和对应生命周期合同。
- 推荐理由：当前目标是规范表示、受控校验和诚实阅读；单文件视图已满足目标，能沿用现有原子保存和归属绑定。尚无流式处理或单独历史存储的要求，不提前引入附件协议。
- 实际答复：用户通过原生 `request_user_input` 选择“单一 JSON 与核心视图（推荐）”。
- 已定合同：保留 JSON/prompt 配对；完整历史只保留一个规范位置，增加原生只读核心视图及按需历史定位。机器全量验证，核心视图阅读不等同于完整历史语义阅读。
- 返回动作：核验 schema 9 的历史门禁与既有收据后，单独决策既有包是否继续允许生命周期操作；当前答复不构成实施批准。

## D3：已有 schema 9 包的兼容处置

- 依赖：D1/D2 已定，必读核心视图与全文阅读有不同语义；新包应明确版本，不能仅改 Skill 后暗中重解释旧 attestation。
- 接口事实：现有新包 schema 9、schema 8 仅只读；`_require_current`、`lifecycle_status`、`ownership status` 按当前 schema 门禁。原生成 prompt 明确全文读取，渲染器不覆盖不同的既有 prompt。旧 schema 的不可变性和只读门禁已有回归测试。
- 选项 A（推荐）：新包 schema 10 采用新阅读合同；schema 9 保持原全文阅读、原接纳/归属合同，增加消费字段及重复投影一致性严格校验。旧 core、prompt、既有收据不改写；schema 8 保持只读。
- 选项 B：新包 schema 10 采用新合同，schema 8/9 均转只读历史。继续正式交接需要从当前事实显式创建新包，不能迁移或改写旧包。最初样本 `20261010T025024334538Z` 也将不能用新版执行 admit/claim 等写操作。
- 推荐理由：修复内部冗余和新增阅读合同不应自动使已封口、未接纳的 schema 9 包失去使用能力；有限的版本分支能保护既有调用方，同时避免把新阅读语义伪装成旧全文阅读。
- 初次答复：原生选择题返回“保留旧合同接纳（推荐）”，尚未开始实施。
- 随后纠正：用户明确表示“不对，我们不需要考虑旧语义兼容”；该最新指令覆盖初次选项。
- 已定合同：新包 schema 10 统一使用核心视图必读、历史按需，不维护 schema 9 全文阅读的接纳或生命周期写分支。历史 core、prompt 和收据保持原样，只保留既有模式的只读检查；不迁移旧包，不执行原样本 pending action。
- 返回动作：按单一当前语义完成方案；旧包不写入、不可用旧声明冒充新阅读声明属于边界回归，不扩展为兼容产品功能。

## 实施结果

- 已按用户最新边界使用 schema 10；schema 8/9 只读，不实现旧全文阅读或 admission 语义兼容，也不迁移历史包。
- 当前 conversation 由共享严格校验器校验；完整公开历史保留于一个 `conversation`，rollout 元数据与 timeline 引用不再复制正文。新 `read` 视图只读、无损分页，历史范围只进原 admission receipt。
- 已覆盖分页、Unicode、长消息、合法空/未知/压缩/NUL/尾部 partial/不完整工具调用、错误交叉引用与边界、历史只读写入口、接纳引用和原样本当前格式投影。
- 大样本仅在内存转换并通过 schema 10 当前校验：原始 44,856,743 bytes，投影估算 21,384,395 bytes（减少 52.3%）；原始文件前后 SHA-256 为 `175fccb175a28f67b9ed28f92e5637ea6bca872b347dfa612d3a0cc5c875da28`，保持不变。该检查没有重写、读取 pending action 或接纳样本。
- 最终检查与组件/根交付证据见 `verification.md`、后续 `deployment.md` 与根任务 acceptance。
