# 渐进决策提问

帮助用户与代理在当前范围内形成可执行的共同方案。非调研任务先筛选重要取舍；有真正需要用户决定的选择时进入本 Skill，不以复杂度、未知项数量或提问次数作为标准。边界清楚的只读研究直接完成证据；研究范围或方法确有用户取舍时仍提问。

## 筛选真正的决策

先复用当前任务、明确指令、证据与已定选择，只补会改变结论的缺口。询问会实质改变范围、体验、职责、权限/数据、部署、成本或验收、且不能由既有约定决定的用户取舍。一个重要选择就足够，不要求多个。

代理核验可查事实并处理局部、可逆、可验证的实现选择；不让用户替代源码检索，不重复问已定事项，不把实施批准伪装成设计问题。无法核实的必要事实明确记为证据缺口，仅在确需用户协助时索取最小信息。

术语或概念的不同解释会改变范围、职责、方案或验收时，先给少量具体情境，比较各解释的行为与后果，并核对当前源码或接口。可查含义由代理核验，真实语义取舍再向用户提问；结论写当前工作的自然落点，不强制建立 Glossary 或 ADR。

## 决策树逐步演进

从当前已知范围建立简要决策链，不要求一次穷举。复用本任务的 PRD、决策或研究记录：重要节点保留问题、依据、选项、推荐及理由、依赖、实际答案及影响；有争议或变化时记下重开条件。证据与局部工程选择由代理关闭，不创建第二状态机或会话配置台账。

多目标、多负责组件、显著风险或多轮访谈时，将原始目标、约束和成功信号链接到重要节点，以及对应要求与验收；在已有计划或矩阵内用简表/标识维持关系。小任务保留足够条目即可，不强制建图，也不要求每项目标都变成用户问题。项目规划、任务状态和最终封口仍由当前项目工作流负责。

| 节点情况 | 下一动作 |
| --- | --- |
| 待证据：问题可描述，但必要事实未核实 | 有界查证后回到该节点 |
| 依赖阻塞：问题可描述，但前序答案或人工前置未满足 | 先处理真实前置，保留阻断关系 |
| 范围内暂不能精确表述 | 保留未知项及受影响目标，待证据或答案展开；不能当作已解决或范围外 |
| 就绪用户取舍：事实和依赖已满足 | 按下述优先级渐进提问 |
| 已决定：有真实答复或可追溯的既定规则/证据 | 保存依据、影响及重开条件 |
| 延期或明确排除 | 分别记录理由及对目标/验收的影响，不能以缺少答案代替排除 |

每轮只选依赖和所需证据已满足的未决用户选择，再按影响与阻断优先级排序。先处理会限制后续方案的边界；后序问题可能因回答新出现、改变或不再需要。

- 本轮只问主题连贯、互不影响的就绪项，数量不超过宿主工具限额，当前为 1–3；只需一问就问一问。
- 如果前序答案会改变后序选项、推荐、范围、风险、修改仓库、负责组件、验证或下一步，后序留到之后的轮次。
- 给出简洁问题、真实互斥选项、推荐和主要后果；不以凑批次、填工具槽位或一次问全为目标。

真实答复先立即写回当前任务，再核验影响、更新分支和重算下一轮。用户自定义答案按实际意图记录，不能强行归入最接近的预设项；部分回答只关闭已答节点。改口或新证据只重开受影响的决定，保留旧结论与原因；淘汰分支标明原因，不反复提问。回答到来后继续规划，不把每轮提问当成任务结束。

答复或证据也可能显露新的重要节点、解除依赖或使分支不再适用；及时更新受影响目标、要求和验收的覆盖关系，再重算就绪前沿。方案比较或验证反馈改变问题定义时，回到受影响节点，不重开无关已定事项。记录复用当前工作已有的自然落点，不另设决策库。

## 有界证据辅助与上下文保护

证据工作可能拉长或分散决策链时，先在当前任务保存待决定节点、缺失事实、影响和返回动作。当前机器与源码用本地工具；外部事实用 `$pennix-grok-search` 或适用的官方检索入口。只取得会改变当前决定的证据，不把整条对话或无关决定外发。

独立证据有明确并行价值且具备授权时，按当前项目的 `trellis-channel` 子节点规程派发；先冻结问题、边界、允许工具、证据保存位置和派发方案，取得专门批准。子节点只核验事实，不替用户决定取舍或修改主任务事实。主代理核验报告后回写原决策节点，再确定就绪问题；派发与等待遵守原生合同，不加轮询、另一套调度器或重复的 Channel 状态定义。

## 原生交互与收口

直接使用当前宿主原生阻塞式 `request_user_input`，不替换为 `request_user_input_async`、代理等待器、shell/MCP 模拟或工具发现探测。不设代理等待上限，不因时间默认采用推荐；只在原生调用实际返回后继续，宿主控制其生命周期。

`request_user_input` 属于宿主原生交互，不要求出现在 MCP 或嵌套工具清单中。`functions.exec` 的 `ALL_TOOLS` 缺项只说明不能从该编排器调用，不能证明宿主直接工具不存在；不要用嵌套清单探测或判断交互工具可用性。当前宿主直接面已声明时按其原生入口和合同调用；拒绝、参数错误、取消或超时保留实际类别，不改报为工具缺失。

宿主拒绝、取消、超时或不可用不构成真实答案；保留必要未决项并停止其依赖动作，允许时用普通文本说明。可选问题空回执服从更高优先级宿主合同，不循环重问，不声称 Skill 能保证宿主无限阻塞，不发明配置键。

就绪项为空时检查：是证据与依赖尚未完成，还是当前范围的重要取舍已明确。前者继续必要且已授权的核验；后者检查方案、修改目标、负责组件、风险和验收是否冲突。不得依据空列表直接封口，也不遍历理论分支或扩展未来需求来延长访谈。

## 规划/实施中的额外发现

发现原始请求之外、可能影响当前任务的事实或缺口时，先核验其是否真实，再记录它与主线的关系、实际修改目标、影响、成本、证据和建议落点。向用户提供“纳入当前任务”“记录后另建任务”“当前范围已有覆盖”“明确排除”四类真实选择；不能静默丢弃，也不能把发现本身当作纳入授权。既有同任务、同修改目标且明确授权的范围可以复用，不重复提问；新增范围仍需单独判断。

纳入规划不等于实施批准。若纳入会改变已封口任务的范围、修改目标、负责组件、部署路径、风险或验收，先按现有 Trellis 生命周期回到规划并重新封口；旁线问题收敛后回读原始请求、主线决策和未决项，再继续主线，不能让额外发现取代主线。

## 最终方案复核

需要规划的 `change_bearing` 工作，必要选择和证据收敛后，先展示完整方案的关键内容：目标与范围、实际修改目标和负责组件、关键决定、验收与验证、发布/安装影响、风险、回退和完成点，并链接当前材料。此时不自动封口；逐项设计问答完成不等于用户已认可整体方案。

再按上述宿主交互合同征询“封口并批准推进”或“补充／修改方案”。前者同时批准该方案的封口与实施，后者保持规划、纳入实际反馈后重新展示。结合上下文识别明确表达同一意图的自由文本，不要求固定口令；用户只同意封口时，仅封口并等待实施授权。设计回答不授予实施权，空回执、取消和推荐项都不构成批准。

明确合并授权只覆盖同一任务刚展示的方案。已初始化 Trellis 项目依次原生 `plan seal`、按成功回执中的 revision `plan approve`、`task.py start`，批准依据保留实际答复摘要，不重复索取同一实施批准。先核对失败步骤和实际状态，不盲目重做已成功的 seal。展示后有实质变化，先更新方案并重新复核；不向其他项目强加 Trellis 命令，不创建第二状态机。

`analysis_only` 完成证据不要求实施批准；直接小改保留原有入口。独立子节点证据仍需冻结派发方案及专门批准，不默认派节点。

## 执行中的新选择

普通实现沿已定选择继续。出现实质未决选择时，立即说明问题、影响与推荐，停止依赖动作并记入当前任务。Trellis 任务已在 `in_progress` 时，先用原生 `task.py replan` 回到 `planning`，再阻塞提问、完善方案，回到最终方案复核。任务已在 `planning` 时更新方案，展示并获明确确认后再重新 `seal`，不误用仅允许 `in_progress` 的 `replan`；不手改 `task.json` 或伪造批准。

用户明确提出同任务、同一修改目标与负责组件、小范围、可逆、低风险增量，且不改变封口实质范围、公开行为、数据/凭据、部署/发布路径或验收时，记录请求、判定和验证后按原生在途路径继续；该请求仅授权精确增量。任一条件不满足或不清楚时回规划处理。缺少原生状态能力时报告缺口，不另建生命周期。

普通继续或充分压缩断点复用已知决定和待办，不重新全量盘点；实际新输入只更新相关节点。当前任务记录是持久依据，提示词不是强制等待、权限隔离或模型行为的确定性保证。
