# 跨组件工作流路由

## 适用范围

任务涉及多个工作流组件、辅助方法组合、阶段衔接，或职责与调用语义无法直接判断时使用本 Skill。方法明确时直接采用，不要求用户点名，也不必先读总路由。普通短问题无需引入额外方法。只加载当前宿主已声明且适用的具体 Skill；不预读整个集合。

## 业务场景与方法组合

先核对当前角色，再采用下文方法。Trellis 团队协作（Trellis Teamwork）的执行者称为 Trellis 团队成员（Trellis teammate；复数 Trellis teammates），仅承接明确的只读研究、审查或验证包；Paseo 并行协作（Paseo-based-parallelism）的执行者称为 Paseo 委派 Agent（Paseo delegated-agent），仅承接主 Agent 已授权的第四阶段实施包。机制、执行者、session、工作树和 attempt 分别命名，原生接口标识保持不变。

两类执行者均不直接询问用户、不代答、不把用户提问工具列为必需能力；缺项、范围外选择或冲突按本机制原生结果合同返回限制、unresolved 或 blocked，由主 Agent 先补证或调整分工，确需用户决定时再询问。读取通用方法不使执行者进入主控需求、方案或阶段接受流程。团队成员只写指定报告；获准的委派 Agent 可在实施包内修改、测试和提交，最终接受、集成与收尾仍归主 Agent／owner。

需要在主集合与 extra 中比较或组合方法时，读取 [全量业务场景](references/skill-scenarios.md)。它说明场景、相邻方法、权限与返回位置；成员及安装来源仍以各自 `collection.json` 和 owner 回执为准。只为阶段衔接时读取 [阶段路由](references/phase-routing.md)，不必同时读取全部引用。

采用方法后完成相关证据或产物，返回当前 task 或任务外请求。读取或披露名称不等于采用；方法不拥有任务阶段、结果接受或动作授权。问题变化、阶段切换和恢复时重新判断适用性，同一问题已有有效正文不重复加载。目标、合同或依赖实质改变时交 Trellis 原生回流；局部问题在已有授权内继续。

## Skill 身份与路径

加载 Skill 前，先从当前宿主清单找到对应逻辑入口，取得该项的声明路径；短路径只按宿主映射展开根别名，保留剩余目录层级并原样读取，不从 Skill 名称反推目录。项目 Skill 可能位于 `<project>/.agents/skills/<skill-name>/SKILL.md`；用户级主集合和 extra 的共享目标分别是 `$HOME/.agents/skills/pennix-skills/<skill-name>/SKILL.md` 与 `$HOME/.agents/skills/pennix-skills-extra/<skill-name>/SKILL.md`。CODEX_HOME 管理宿主配置，不选择共享集合版本；system、插件和其他原生 owner 保留自己的声明位置。这些例子不替代本轮声明，也不是依次重试的候选表。Skill 的相对引用以实际加载文件所在目录为基准。若无法确认实际路径，保留原始回执并停止，不通过平铺路径重试，也不因路径猜测失败判定 Skill 或宿主工具不存在。以首次实际读取及其回执核验完整路径，后续成功不能抹去首次错误。

## 调用前判定

跨组件请求或接口不清时，先判断请求和交付范围，再选择工具。单个工具已有明确协议时直接遵守；执行载体不改变负责组件。将必要判断写入当前任务或返回调用方：

- `work_domain`：工程/工作流治理、系统部署、项目 Trellis 资产更新或普通本地操作；
- `delivery_mode`：受保护目标不变的精确证据交付，或 change-bearing；
- `execution_class`：负责组件、范围和验证都可立即确定的 `direct`，或需要完整方案的 `planned`；
- `decision_frontier`：是否存在尚未由既有约定决定的重要用户取舍；
- `approval_mode`：是否已有针对当前整体方案的明确接受与实施授权；同一真实答复可明确批准二者，但分别交项目原生接口记录。普通设计选项回答不自动批准整体方案，已有充分授权不重复询问；实质变化只重核受影响部分。

`analysis_only` 表示受保护目标不变的只读证据交付；复杂度、跨组件、多证据单元、推荐或未决产品选项本身不触发实施批准。明确研究请求授权主会话完成证据工作；研究范围或方法依赖尚未回答的用户选择时，再调用 `$pennix-decision-grill`。Teamwork 派发遵守当前项目规则与实际授权，只交付列明的只读证据。实际变更、部署、发布、凭据或外部运行态动作仍按负责组件的变更授权流程处理。

判定结果中的 `owner` 表示负责该操作并规定调用接口的组件，`allowed_transport` 表示允许入口，`state_writer` 表示状态写入组件，`exit_conditions` 和 `replan_trigger` 表示停止与重新规划条件。源码维护仓库、安装工具和状态写入组件可能不同，应分别说明，不能以宽泛代称混为一谈。这不是第二套状态机，各组件仍维护自己的状态。

除有界只读研究外，先筛选重要用户取舍；一个就绪选择也可进入 `$pennix-decision-grill`。渐进问答由该 Skill 负责。执行中出现实质未决选择时，说明影响并暂停依赖动作；拉长证据工作前先保存决策节点和返回动作，再调用规定的检索入口。

## 判定顺序

先看操作语义和规定接口，再看工具名称。工具可用性、位置或通用能力不改变组件职责：

| 调用语义 | 首选路径 | 事实与持久化边界 |
| --- | --- | --- |
| Trellis 任务/阶段、组件 CLI 与系统部署 | 使用 owner 的真实命令和接口；符合当前调用语义时可由 Context Mode 执行并分析回执 | Context Mode 不接管 owner 协议、状态写入或授权；不以 shell 模拟专属协议 |
| Teamwork continuation、Codex 交互/Hook、原生 MCP/TUI | 对应宿主或组件原生入口 | 保留实时状态与排他等待，不包装宿主总线 |
| 宿主工具面与 Hook 路由核验 | 按当前问题核对宿主直接声明、编排器嵌套工具、MCP 或 Hook 的实际入口；不必每次穷举所有层 | Codex 的 `request_user_input` 等直接工具不要求出现在 `functions.exec` 的 `ALL_TOOLS` 或 MCP 清单中；其他宿主按其真实声明核验。执行者无需用户提问工具；局部缺项不代表宿主缺失，参数、用途、权限和环境失败保留原类别 |
| Grok、Tavily、Windsurf、CodeGraph 或 `openai-docs` 检索 | 先按问题选择来源，再按其真实 MCP／CLI 接口调用；MCP 直接调用，大输出可按需交 Context Mode 分析 | 载体不接管来源、凭据、认证输出或降级；已送入上下文的 MCP 输出再复制到执行器不能追回上下文成本 |
| 源码、配置、任务文档等文本的语义创建/修改 | Codex 使用宿主原生 `apply_patch`；其他宿主使用其声明的原生语义编辑入口 | 先满足当前角色与目标的写入授权；不通过执行器或 shell/Python 写入脚本代写，生成资产仍由其生成接口写入 |
| 自定义中文技术文档的撰写、改写、校对或审阅 | `$pennix-chinese-tech-writing`，按内容加载参考 | 新增技术文档默认中文，明确语言要求除外；Trellis 原生机械惯例优先，编辑、任务状态和保存仍走各自接口 |
| 日常答复、复杂交付或批准前方案展示需要检查覆盖、详略、重点、结构或图表关系 | `$pennix-agent-output-quality`；中文技术内容再组合 `$pennix-chinese-tech-writing` | 输出质量 Skill 负责内容组织和语义复核，语言 Skill 负责中文表达与保真；简单事实走短路径，不改变任务状态、批准或安装 owner |
| 普通本地文件、非交互命令、构建/测试、递归检索或大输出分析 | 遵循当前宿主与 Context Mode v2 的原生行为；小而有界的输出直接读取，需要筛选、计算或压缩大输出时使用 Context Mode | 支持输出替换的宿主先执行再处理真实输出；全文要求须完整取得，索引与摘要不能代替全文 |
| 已配置服务的健康检查、有限查询或读取 | 直接调用当前会话中可用的 MCP 工具 | 若工具未绑定到当前会话，报告能力缺口并停止；不要改走 shell HTTP |
| 已批准项目的符号、调用关系、架构或影响范围 | 优先可用 CodeGraph，边界见下节 | 返回源码区段可复用；缺失或陈旧部分再核验，不机械重读；未批准项目不得自动启用索引 |
| 含义与范围明确但没有有效代码锚点的业务、历史或遗留代码定位 | `$pennix-windsurf-code-search` 可直接发现候选，既有外部边界不变 | 不强制先 rg／图查询；候选在 Context Mode 内核验当前源码，关系再交 CodeGraph |
| 加载并遵守项目外 AGENTS.md、SKILL.md 及其必读引用 | 宿主原生入口完整读取，不先尝试 Context Mode | 仅指指令加载；普通项目外数据按实际文件工具权限和来源合同处理 |
| 当前外部资料、网页或多来源研究 | 优先 `$pennix-tavily-search`；当前操作适合 Grok 或用户/路线明确选择 Grok 时使用 `$pennix-grok-search` | 来源 owner 保留发现和认证合同；已取得资料可由 Context Mode 按来源合同处理/索引，写入任务事实前仍核验 |
| 长任务或跨轮后台执行 | 按需选择可保留所需运行语义的真实执行接口 | 任务时长本身不排除 Context Mode；需要宿主交互或当前接口无法续接时走对应宿主入口 |
| 已有工具支持文件输出的大型结构化结果 | 原工具先写入已批准文件，再用 context-mode 限定分析或原生分页读取 | 不把原始结果重新塞回工具参数，分析结果不自动晋升为任务事实 |
| 工作流缓存、Teamwork、输出、备份或历史资源的盘点与清理 | `$pennix-resource-cleanup`，再转资源 owner 的原生清理入口 | 默认只读；精确预览和明确授权后才允许 owner 执行 |
| 项目 AGENTS 来源、内部生成块、内容职责或冲突；明确授权的项目初始化、重初始化、刷新或移除 | `$pennix-project-agents-governance` | 默认只读；已授权动作固定项目根、宿主和选定组件，由主 Agent 串行调用原生 owner，逐步回读、失败重入并联合核验 |
| 建立或刷新项目 `.trellis/spec/` 规范 | 宿主实际声明的 `trellis-spec-bootstrap` | 复用当前任务与授权，从源码整理实际主题；入口准备不等于规范有效，未声明时报告限制，不猜路径或自动安装 |

Context Mode 的工具参数与宿主适配以当前 MCP instructions、工具声明和原生 help 为准。owner 决定操作语义、权限和状态；其真实非交互命令可由 Context Mode 承载，前提是本次所需身份、参数、退出码与回执均可保留。不得用 shell HTTP、自造 JSON、后台化或代理轮询替代组件协议。

宿主专属协议（例如 `apply_patch`、用户审批、宿主 MCP、视觉渲染或实时 continuation）使用真实宿主接口。项目外指令加载按上表直接原生全文读取。Context Mode 不可用、调用失败或无法保留必要身份、交互、取消、续接语义时，核对是否已执行，再为本次调用使用获准的原生入口；不把一次失败扩大为组件整体不可用。权限拒绝必须遵守，不能换载体绕过。项目外普通数据按宿主权限访问；项目库范围不构成全局执行器的文件访问禁区。Hook 行为取决于实际 adapter 与宿主能力，不能声称全部工具都被接管。

强制全文材料必须沿真实分页取得完整原文；输出被索引或截断时继续读取缺失范围，必要时使用允许的原生入口。上游的单次读取大小限制支持有界分页，与访问授权拒绝分别判断；项目外指令仍通过原生入口分页读取，不转入执行器。实际权限或信任拒绝必须停止。自动恢复和索引是历史参考，当前指令、原生任务状态及授权仍为权威。Codex 原始 sessions/memories 归宿主；Context Mode v2 默认使用 `~/.context-mode`，按 Git common directory 确定共享项目库，worktree 不等于独立清理边界。数据库自愈遵循上游；安装、配置和版本更新归 Lifecycle。

Trellis `task.py current --json` 的 `session_source` 表示身份，`source=unbound_task|unbound_ambiguous` 表示尚未绑定任务，两者分别判断。有身份时按用户明确意图原生 `select`，再遵守任务阶段。载体无法核验身份时使用宿主原生 shell；禁止复制环境身份、借用其他会话 pointer 或制造 shell ticket。

新请求由宿主声明的 `trellis-request-intake` 判断与当前任务的关系及 taskless 适用性；会话初始化与恢复分别由 start、continue 处理。目标探索、候选构造和整体方案收敛由当前阶段 Skill 负责，结果接受和实施授权分别由 Trellis CLI 写入。`pennix-decision-grill` 只处理重要用户取舍与交互方法。已授权局部修复直接继续，实质变化回最早受影响阶段，独立工作另行接入；不复制阶段状态或猜造旧接口。

## 各业务阶段中的组件路由

任务涉及 Trellis 阶段、协作、辅助 Skill 或交付收尾时，读取 [阶段与辅助组件路由](references/phase-routing.md)。阶段状态与授权仍由 Trellis 原生接口维护。

## 代码检索：先选来源，再选载体

已知路径和字面量直接查当前文本；已批准且索引可用项目的符号与影响问题优先 CodeGraph；含义与范围明确但缺少有效代码锚点时才考虑 Windsurf。需要代码定位或结构分析时，读取 [代码检索的来源与核验边界](references/code-search-routing.md)。

## 当前 Trellis fork 并行工作流

需要并行协作时，读取 [并行工作入口](references/teamwork-routing.md)：只读证据使用当前 `trellis-teamwork`，已授权完整结果包的独立工作树实施使用当前 `trellis-worktree-delegation`。各自走原生入口，工具可见不替代派发授权。

## 本地证据优先

- 涉及当前机器、当前项目、工作树、源码、配置、日志或已存在资源时，按上节选择 CodeGraph、精确文本或无锚点语义定位；适用 CLI 与文本处理按输出和宿主能力选择载体，项目外指令加载遵守原生全文例外。本地证据已足以回答时，不启动外部检索。
- 本地存在目标源码但问题要求当前上游状态、公开资料、跨项目比较或外部事实时，才进入外部检索；外部检索结果仅补充或对照本地证据，不能替代本地事实核验。
- 本地检索结果为空、过时或无法解释时先保留具体缺口，不能自动扩大外部范围。外部事实用网页检索，语义代码候选用上节 Windsurf 条件；用户明确指定来源时优先遵守，同时保留任务和凭据边界。
- `$pennix-grok-search` 的可发现性不构成自动调用理由；调用前必须先判断问题是否确实需要外部资料。

## 外部检索来源选择

- 当前任务需要外部检索时优先使用 `$pennix-tavily-search`。操作失败遵循其 Skill 对请求前本地错误与请求后错误的区分：核实是否已执行，再选择允许的入口；不盲目重试或改用其他服务商。用户指定来源或工具时，按该请求选择相符入口。
- 仅在当前操作适合 Grok（例如需要 X 来源）或用户/路线明确选择 Grok 时使用 `$pennix-grok-search`。遵守该 Skill 的调用与失败合同；不因其可发现就自动调用，也不在失败后自动切换服务商。

## 组件职责

项目初始化和退出涉及共享 `AGENTS.md` 时，先由治理 Skill 按[项目操作编排合同](../pennix-project-agents-governance/references/project-operations.md)核对 writer、全局／用户层 writer、消费者与可选／未知项，再调用已选 owner。系统部署交 Lifecycle，已管理 Trellis 资产更新交 project-update，CodeGraph 项目接入沿原生 local install；项目接入不隐含索引授权。保留成功项、停止失败依赖，从失败 owner 最小重入；两种 owner 顺序与最终文件、配置及加载限制共同核验。此入口不增加 CLI、执行器、registry、台账或全局事务保证。

涉及知识、历史、正式交接、项目资产更新、部署或资源清理时，读取 [专项组件归属](references/component-ownership.md)。知识与规则晋升另见 [知识晋升边界](references/knowledge-promotion.md)。

## 禁止混淆

- Context Mode 的索引、摘要和恢复材料不自动成为 task、Issue、授权或配置事实；关键结论回到当前权威来源核验。
- 不用执行器重实现 Trellis Teamwork 事件等待、Hook 交互或其他已有专用协议；不通过轮询替代生命周期等待。
- `$pennix-tavily-search` 负责一般外部检索，`$pennix-grok-search` 负责适合 Grok 或明确选择 Grok 的检索；各自保留来源、认证和失败合同。`openai-docs` 负责其允许的 OpenAI/Codex/API/ChatGPT 官方资料路径；官方来源要求优先走对应官方入口。
- 不因“用户希望并行”就自动派发 worker；没有独立证据价值时保留主会话 inline 路径。
- 不将凭据、会话、缓存、数据库、日志、运行态、原始外部响应或未经核验的候选提交到 Git；Context Mode 本地索引按原生工具、用户指令和来源 owner 合同处理，可保存带来源及未核验状态的候选。
